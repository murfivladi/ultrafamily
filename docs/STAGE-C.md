# Этап C — общение, совместная работа и realtime

Этот документ описывает внутреннюю техническую сборку **Этапа C** по разделу 34 исходного [ТЗ](TZ-original.md). Она расширяет [Этап B](STAGE-B.md) и, как и предыдущие этапы, **не является публичной версией 1.0**: первая публичная версия по ТЗ выпускается только после реализации всего выбранного объёма.

## Архитектура и потоки

- Браузер использует относительные `/api/*` URL. Next.js проксирует HTTP к API. Для realtime добавлен отдельный WS-прокси: HTTP-реврайт Next.js не умеет upgrade соединения, поэтому `/ws` проксируется `scripts/ws-proxy.mjs` (в dev/preview) или reverse proxy в production.
- Прокси слушает `WS_PUBLIC_PORT` (по умолчанию 26288) и передаёт обычные HTTP-запросы в Next.js, а `Upgrade: websocket` на путь `/ws` — в NestJS. Это единственный хоп; медиа WebRTC через прокси **не идёт**.
- Все REST-маршруты проходят `AuthGuard`, CSRF для изменяющих методов и `AccessService.assert(...)` (пространство, членство, роль, модуль, действие, точечные права, детские/гостевые ограничения).
- Gateway (`CollaborationGateway`) аутентифицирует соединение по cookie сессии **до** `hello` и закрывает его кодами `4401` (нет сессии) и `4403` (нет CSRF/чужое пространство). Проверка `Origin` выполняется, если задан `APP_ORIGIN`.
- `hello` возвращает `ready` со списком сессий присутствия; подписка ограничена темами, на которые у пользователя есть права.
- Yjs-комнаты живут в памяти API-процесса, документ гидрируется из `documents.content`, обновления сохраняются с дебаунсом `SAVE_DEBOUNCE_MS = 1200` и записываются в `document_versions` при изменении текста. Клиент, потерявший соединение, при реконнекте отправляет `doc:request-state` и получает полное состояние с `reason`.
- Идемпотентность: сообщения, голоса, реакции и сигналы несут клиентские ключи; сервер отбрасывает дубликаты, поэтому повторная отправка после обрыва не создаёт второе сообщение.

## Схема

Аддитивная миграция `005_stage_c.sql` создаёт 29 таблиц и не меняет существующие данные Stage A/B; повторный запуск идемпотентен, версия записывается в `schema_migrations`. Ключевые таблицы:

- messenger: `chats`, `chat_members`, `chat_messages`, `chat_message_versions`, `chat_reactions`, `chat_attachments`, `chat_receipts`, `chat_moderation_log`;
- лента и решения: `feed_posts`, `feed_comments`, `feed_reactions`, `space_governance`, `polls`, `poll_votes`, `proposals`, `proposal_votes`, `decision_history`, `wishlists`, `wishlist_items`;
- документы: `documents`, `document_versions`, `document_collaborators`, `document_comments`, `document_presence`;
- WebRTC: `call_rooms`, `call_participants`, `call_signals`, `call_events`;
- realtime: `collaboration_presence`.

Демонстрационное содержимое Stage C (чат семьи, прямой чат, канал «Объявления», пост с комментарием, опрос «Куда поедем летом?», предложение, вишлист, документ «Семейные заметки») создаётся только при первом запуске пустой базы и только вне production (`SEED_DEMO_DATA !== 'false'`).

## Протокол `/ws`

Клиент → сервер: `hello`, `subscribe`, `presence`, `cursor`, `doc:sync`, `doc:request-state`, `call:signal`, `call:state`, `ping`.
Сервер → клиент: `ready`, `pong`, `presence:list`, `cursor`, `doc:state` (с `reason`), `doc:update`, `doc:rejected`, `call:signal`, `call:state`, `error`.

Сериализация Yjs-обновлений — base64 внутри JSON, максимум 512 КБ на кадр (крупнее — закрытие соединения). Типы обеих сторон объявлены в `packages/contracts/src/stage-c.ts` (`CollaborationClientMessage` / `CollaborationServerMessage`).

## Права и приватность

- Дети получают `messenger` и `decisions` на уровне `coreRead`: читать и участвовать в семейных решениях можно, удалять, публиковать, экспортировать и управлять доступом — нельзя.
- Гость читает только явно расшаренные материалы; в чаты и документы по умолчанию не попадает.
- Платформенный администратор не получает семейные данные даже при искусственном членстве.
- Все изменения (сообщения, реакции, публикации, голоса, решения, документы, доступы) пишутся в аудит; приватные тела не дублируются в realtime-событиях.
- Нет скрытой геолокации, баллов, публичных рейтингов и автоматической публикации внутренних данных наружу.

## WebRTC: эксплуатационные границы

- Медиа идёт напрямую между браузерами (P2P) или через TURN. Оно **никогда** не проходит через обычный HTTP-деплой, Next.js-прокси или Cloudflare Origin Rules: такие правила не рассчитаны на UDP/SRTP и ломают соединение.
- STUN задаётся `WEBRTC_STUN_URLS`; TURN — `WEBRTC_TURN_URLS`, `WEBRTC_TURN_USERNAME`, `WEBRTC_TURN_CREDENTIAL`. Если TURN не задан, `GET /api/calls/rooms/:id/diagnostics` возвращает `turnConfigured: false`, и интерфейс явно предупреждает, что за симметричным NAT соединение не установится.
- Оффер всегда создаёт участник с лексикографически меньшим `userId` — это исключает «glare» без полной реализации perfect negotiation.
- Перед production нужен отдельный сетевой и нагрузочный тест: TURN на собственном хосте, проверка мобильных сетей, ограничение полосы, лимит участников и мониторинг `call_events`.

## Тестирование

`npm run check` выполняет typecheck контрактов/API/web, 8 unit-тестов прав и 36 серверных E2E/интеграционных тестов. Stage C покрывает (`stage-c.e2e-spec.ts`, `collaboration.e2e-spec.ts`):

- создание чатов, отправку сообщений, реакции, закрепление, ветки, прочтение, поиск и модерацию;
- ленту: посты, комментарии, реакции, источники, автоматические события;
- опросы (включая ничью и кворум), предложения, вишлисты, историю решений и правила голосования;
- документы: версии, восстановление, комментарии, права и коллабораторов;
- комнаты WebRTC, участие, сигналы и диагностику ICE;
- WebSocket: отказ без сессии (4401), отказ без CSRF (4403), `hello`/подписка/`ping`/presence, Yjs-синхронизацию с сохранением в базу, сигналинг WebRTC и `/signals`.

Дымовая проверка `scripts/smoke.sh` дополнительно убеждается, что gateway на `/ws` отвечает на upgrade-запрос (101/401/403), а не отдаёт 404.

## Известные границы

- Полноценный офисный редактор (таблицы, презентации, предпросмотр PDF/office) не реализован. Совместное редактирование работает для текстового содержимого документа; таблицы и презентации хранятся как типы с текстовым телом, а предпросмотр файлов появится вместе с файловым модулем Этапа D.
- Yjs-комнаты живут в памяти одного API-процесса. Для многоэкземплярного развёртывания нужен общий транспорт (Redis pub/sub) и внешнее хранилище состояния; сейчас это ограничение задокументировано, а не замаскировано.
- TURN-сервер не развёрнут в этой среде. STUN работает, диагностика честно сообщает `turn_not_configured`; без TURN соединение за симметричным NAT не установится.
- Реальное двустороннее аудио/видео между двумя браузерами, мобильные сети, демонстрация экрана на iOS и нагрузочное тестирование signaling не проверялись в этой среде — для них нужен отдельный сетевой стенд.
- Вложения чата хранят метаданные и ссылку; загрузка, антивирус и превью относятся к Этапу D.
- Web Push/email/Telegram-адаптеры по-прежнему не подключены: уведомления Stage C доставляются in-app и через realtime.
- Браузерные Playwright-тесты, production PostgreSQL/Docker runtime и `npm audit` в этой среде не запускались.
- Экспорт истории чата и документов в ZIP/JSON целиком входит в Этап H; текущий экспорт ограничен существующими CSV/ICS механизмами Stage B.
